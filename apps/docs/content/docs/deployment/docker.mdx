Docker Compose is the simplest way to run Everstack yourself. It suits local
development, evaluation and small single-node installs.

<Callout type="info">
  Everstack's container images are not yet published to a public registry, so
  this guide builds the image from the open-source repository. Pulling
  `ghcr.io/everstacklabs/everstack` from outside Everstack does not work today.
</Callout>

## Prerequisites

- Docker Engine with Compose v2
- About 6 GB of memory for the first build
- Git

## Start the quickstart

The repository ships a Compose file that builds the Community Edition and starts
it with PostgreSQL:

```bash
git clone https://github.com/everstacklabs/everstack.git
cd everstack
docker compose -f examples/quickstart/compose.yaml up -d --build
curl --fail --retry 30 --retry-delay 2 --retry-all-errors http://localhost:8089/debug/healthz
```

Then open [http://localhost:8089](http://localhost:8089), register the first
account (it becomes the instance owner), add a model-provider key under
**Vault → LLM Providers**, create an Everstack API key under
**Vault → API Keys**, and send a request:

```bash
curl http://localhost:8089/v1/chat/completions \
  -H 'content-type: application/json' \
  -H "Authorization: Bearer $EVERSTACK_API_KEY" \
  -d '{"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "Hello"}]}'
```

The `x-evs-api-key` header works as well. The bearer form is accepted
on the OpenAI-compatible routes under `/v1`.

## What the quickstart runs

| Service | Purpose | Port |
| --- | --- | --- |
| `everstack` | Gateway, API and embedded admin dashboard, built with the `ce` tag | `127.0.0.1:8089` |
| `postgres` | PostgreSQL 16 with pgvector, for platform state | not published |

It leaves out ClickHouse, Redis and sandbox access, runs with telemetry switched
off (`EVS_TELEMETRY_ENABLED=false`). Sign-in is on (`EVS_AUTH_MODE=builtin`):
the first account you register becomes the instance owner. The
[quickstart README](https://github.com/everstacklabs/everstack/blob/master/examples/quickstart/README.md)
explains what each omission means.

## Configuration

Settings come from three layers, highest priority first:

1. Environment variables with the `EVS_` prefix
2. A YAML file passed with `--config`
3. Defaults embedded in the binary

Commonly used variables:

| Variable | Meaning |
| --- | --- |
| `EVS_DATABASE_MODE` | `single` (PostgreSQL only) or `hybrid` (PostgreSQL and ClickHouse) |
| `EVS_POSTGRES_DSN` | PostgreSQL connection string |
| `EVS_CLICKHOUSE_DSN` | ClickHouse connection string, for `hybrid` mode |
| `EVS_CACHE_TYPE` | Cache backend, for example `memory` or `redis` |
| `EVS_CACHE_REDIS_ADDRESS` | Redis address when the cache type is `redis` |
| `EVS_AUTH_MODE` | `none`, `builtin` or `oidc` |
| `EVS_API_KEY_HASH_SECRET` | Secret used to hash Everstack API keys. Required. |
| `EVS_LOG_LEVEL` | Log level, for example `info` |

The complete list of supported variables, with the config key each one sets, is
in
[`cmd/config/gateway/validator/envvars.go`](https://github.com/everstacklabs/everstack/blob/master/cmd/config/gateway/validator/envvars.go).

To use a YAML file instead, mount it into the container and pass it to `serve`:

```yaml
everstack:
  command: ["serve", "--config", "/app/config/everstack.yaml"]
  volumes:
    - ./everstack.yaml:/app/config/everstack.yaml:ro
```

Example files are in the repository's `examples/` directory.

## Migrations

The gateway applies its PostgreSQL migrations at startup, and its ClickHouse
migrations too when `EVS_DATABASE_MODE` is `hybrid`. No separate migration step
is needed before the first start or after an upgrade.

## Tracing

Traces, logs and the observability views are stored in ClickHouse. With only
PostgreSQL, as in the quickstart, those views stay empty. To store traces, run
ClickHouse and set:

```yaml
environment:
  EVS_DATABASE_MODE: hybrid
  EVS_CLICKHOUSE_DSN: clickhouse://USER:PASSWORD@clickhouse:9000/everstack
```

In hybrid mode the gateway also accepts OpenTelemetry traces from your own
applications over OTLP/HTTP at `/api/public/otel/v1/traces`, authenticated with
an Everstack API key. A tested Compose file for this setup is not published yet.

## Sandboxes

The Docker sandbox backend needs access to a Docker daemon, which is equivalent
to root on the host, and the default sandbox images are not yet in a public
registry. The quickstart does not enable sandboxes, and there is no tested
self-hosting guide for them yet.

## Health checks

The gateway serves a health endpoint at `/debug/healthz`. The image includes
`wget`, and the quickstart uses it for the container health check:

```yaml
healthcheck:
  test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:8089/debug/healthz"]
  interval: 5s
  timeout: 5s
  retries: 30
```

## Data and volumes

PostgreSQL data lives in the `postgres-data` named volume and gateway data in
`everstack-data`, so both survive container restarts.

<Callout type="warn">
  `docker compose down --volumes` deletes the named volumes and all data in
  them.
</Callout>

## Upgrading

Pull the new source and rebuild. Migrations run when the new container starts.

```bash
git pull
docker compose -f examples/quickstart/compose.yaml up -d --build
```

## Before exposing it to a network

The quickstart's database password and API-key hash secret are examples. Replace
them, keep sign-in on, put TLS in front of the gateway, and back up the
PostgreSQL volume.
